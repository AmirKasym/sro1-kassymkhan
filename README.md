## 3. Ответы на вопросы
1. Почему размеры v1 и v2 различаются именно так?
   В чём главная польза многоэтапной сборки в этом проекте?

   Оба образа сделаны на python:3.12-alpine, а он сам весит около 83MB, поэтому разница небольшая: 84.5MB против 83MB. Наши файлы маленькие, и в v1 лишнее - это вся папка проекта (tests, data, tools, web, logs, Dockerfile.v1), а в v2 только server.py и report.json. Главная польза многоэтапной сборки в том, что тесты запускаются прямо во время сборки, и образ с плохими данными просто не соберётся, а в рабочий образ не попадает ничего лишнего.

2. Какой тест упал на этапе 3? Почему не появился образ koktobe-lift:bad?

   Упал test_hour_limit: после ошибочной записи KT9999 за 2026-10-04 в 12:00 получилось 43 пассажира, а лимит 40 (AssertionError: 43 not less than or equal to 40). Команда RUN python -m unittest вернула exit code 1, и Docker остановил всю сборку. Поэтому образ koktobe-lift:bad не создался, в docker image ls его нет.

3. Какие шаги на этапе 4 были CACHED и почему?
   Какие шаги выполняются заново при изменении records.csv?

   На этапе 4 я поменял только app/server.py, поэтому все шаги стадий build и test (WORKDIR /src, COPY tools, COPY data, RUN build_report.py, COPY tests, RUN unittest) и COPY --from=test были CACHED: их файлы не менялись. Заново выполнился только COPY app/server.py в финальной стадии. Когда я для проверки поменял одну строку в records.csv, CACHED остались только WORKDIR и COPY tools/, а COPY data/ и всё после него (генерация отчёта, тесты, копирование report.json и server.py) выполнилось заново, и контрольный код поменялся. В итоговом Dockerfile server.py копируется раньше report.json, поэтому при смене данных COPY app/server.py остаётся CACHED.

4. Что было бы, если бы финальная стадия брала report.json
   не из стадии test, а из стадии build?

   Тогда BuildKit увидел бы, что стадия test финальной стадии не нужна, и просто не стал бы её выполнять. Тесты бы не запускались, и образ с ошибочной записью KT9999 спокойно собрался бы. То есть данные, нарушающие правило 40 пассажиров в час, попали бы в рабочий образ.

5. Как контейнер web находит контейнер API? Почему внутри
   контейнера web адрес localhost:8080 не работает?

   Оба контейнера подключены к одной сети lift-net, и Docker внутри сети сам превращает имя контейнера в IP-адрес. Поэтому в nginx.conf написано proxy_pass http://lift-api:8080, и nginx находит API по имени lift-api. А localhost внутри контейнера web - это сам контейнер web, там работает только nginx на порту 80, а API на 8080 там нет.
